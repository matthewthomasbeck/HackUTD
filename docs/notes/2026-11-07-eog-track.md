## The challenge ("Beat the Shutdown")

Build a console for night-shift operators of a produced-water network.
Wells fill a tank, a pump empties the tank into a pipeline, and the pipeline goes to a disposal site.
Each facility has a few wells, one tank, one pump, and one pipeline.
A system is a group of facilities that share one disposal site and a small truck fleet.

The app must find three problems from the sensor readings only:

| Problem | Required action |
| --- | --- |
| `pipeline_leak` | Urgent alert, send an inspector (`field_inspection`) |
| `pump_degradation` | Alert, send an inspector (`field_inspection`) |
| `pump_failure` | Countdown to the tank's shutdown limit, and the cheapest plan: send trucks, shut in wells early, both, or do nothing |

Two or three pumps in one system can fail within an hour of each other, and they share the system's 2 or 3 trucks.
The README calls this the hard case.

## Data

- Each dataset folder has `network.json`, `ops.json`, and `telemetry.csv` (every sensor every 5 minutes).
- `history/full_week/` is one week of systems S1 to S5 with 23 labelled events (13 pump failures, 5 leaks, 5 pump degradations) in `answer_key.json`.
- Three snapshot folders cut the same week early with problems in progress, and a mock test folder has no answer key.
- Right before judging, organizers add `test/`, a week from a new network (S6 to S11) with no answer key.
- The app must load any folder with no code changes.
  `answer_key.json` is for self-checking only and must never be loaded by the app.
- Costs and rules (truck trips, shut-in lost revenue, repair times, shared trucks) are in `ops.json` and `SPEC.md`.
- The repo also contains the organizers' own `CLAUDE.md`, which describes organizer-only files and some details of the hidden test week.
  Treat that as off limits.
  Build a general detector and do not tune to it.

## Judging (repo README)

Creativity, user experience and aesthetics, usefulness and functionality, how correct and optimal the cost plans are, data from the files with no hardcoding, and following the instructions.

## What EOG said (AI summary of the conversation)

- The core is data: train on the provided data, then test on a separate dataset with different values, find the problems, and suggest a next step.
- A key need is to tell a real problem from a faulty or misleading sensor reading, so people are not sent out for nothing.
- EOG described a proactive, autonomous approach that verifies an alert before field staff arrive.
- A drone or robot can make the demo more visual (for example, surveying a tank), but the hardware must support the data challenge, not replace it.
- The same summary says CBRE questioned who would control a drone, and that the "RoboDock" idea did not land well.
- Its conclusion: for both EOG and CBRE, the common thread is reliable data that leads to a useful, verified action, and the robot is an optional way to collect or confirm information.
